# Pane contents come from `herdr terminal session observe`

warpr renders a pane by running `herdr terminal session observe <pane> --cols N --rows N` as a subprocess and feeding each frame's decoded `bytes` into Warp's existing VT grid. Frames are JSON lines (`type: "terminal.frame"`, `seq`, `full`, `width`, `height`, `encoding: "ansi"`, base64 `bytes`): the first is a full repaint, later ones are incremental cursor-positioned repaints. This avoids both polling `pane.read` snapshots and speaking Herdr's undocumented binary protocol.

If `herdr status` reports the private protocol as incompatible with the installed binary, warpr refuses to connect and says why, rather than degrading to the public API.

ADR-0003 supersedes the observe-only default: observe is now the fallback for panes that another client owns. The frame format and the findings below still apply.

## Considered Options

- Poll `pane.read --format ansi` over the public API: stable but not live, and weak for mouse, alt-screen and cursor fidelity.
- Speak Herdr's numbered binary protocol directly: same-install only and undocumented, so it would lock warpr to exact Herdr builds.
- Attach a Herdr client in a PTY and render that: faithful, but it brings the client's prefix key and single-owner input contention into every view.

## Consequences

- Frames were observed streaming over plain pipes (held-open and `/dev/null` stdin); no PTY is needed per pane.
- Input ownership and the take-control path are specified in Spike findings, section 2. The earlier `terminal.closed` / `detached` with `/dev/null` stdin was stdin EOF, which `control` treats as a detach.
- Wide characters and alt-screen applications pass through `observe` correctly; Kitty images do not (section 3).
- Observe cannot be resized in place and its `--cols`/`--rows` crop the pane rather than resizing it (section 1), so a pane's text is never re-wrapped to warpr's size.
- warpr must pass an explicit socket for the chosen session; an inherited `HERDR_SOCKET_PATH` points at whichever session the launching shell lives in.

## Spike findings

Spike #3, run against Herdr 0.9.3 (private protocol 22) on macOS arm64, in an isolated session `warpr-test` (a headless `herdr --session warpr-test server`, stopped afterwards; the default session was never addressed). `herdr` below stands for the isolated invocation `env -u HERDR_PANE_ID -u HERDR_TAB_ID -u HERDR_WORKSPACE_ID HERDR_SOCKET_PATH=~/.config/herdr/sessions/warpr-test/herdr.sock HERDR_SESSION=warpr-test herdr`. Streams were read through plain pipes and decoded with `pyte`; ground truth was `herdr pane read --source visible`. Source references are to the `v0.9.3` tag of `herdrdev/herdr`; the `terminal session control` stdin protocol is also documented in the 0.9.4 CLI reference ("Direct terminal attach").

### 1. Resizing: observe cannot be resized in place

- **No in-place resize.** `observe` never reads stdin (`src/client/terminal_sessions.rs`). Sending `{"type":"terminal.resize","cols":90,"rows":30}` on the stdin of a running `herdr terminal session observe w1:p1 --cols C --rows R` (C×R = 120×40, 60×20, 200×60) produced no frame, no stderr and left the process running. The server does track a viewport per observer, but only the private binary protocol can change it.
- **Restart is the mechanism.** A new `observe` process starts at `seq: 1`, `full: true`, `width`/`height` equal to the requested `--cols`/`--rows`. Spawn to first frame was 191–279 ms (median 266 ms, 10 runs over 80×24 … 200×50). Observers are not exclusive, so warpr can start the new stream first and kill the old one after its first frame (a second observer at 100×30 streamed beside a live 80×24 one).
- **`--cols`/`--rows` are a viewport, not a pane size.** The pane's PTY did not change (`stty size` printed `40 120` before and after observers at 120×40, 60×20 and 200×60). A 110-character line was cut to 60 characters at `--cols 60` and was not re-wrapped; a 40×10 viewport on a full 120×40 screen showed the top rows (`62`…`71` of `seq 1 100`), anchored top-left. A larger viewport pads with blanks. Text is therefore never reflowed to warpr's window size by `observe`.
- **What does set the PTY size.** (a) A headless server defaults to 120×40. (b) A Herdr TUI client's layout pass: a client attached at 100×30 made the pane `29 74` (`stty size`; `pane layout` area 74×29), and resizing it to 140×45 made it `44 114`; a running observer at fixed 120×40 then received a `full: true` frame mid-stream (`seq 4`), so `full` can arrive at any time, not only first. (c) A controller (below). With no TUI client attached, layout does not resize PTYs: after `pane split`, `pane layout` reported two 60×40 rects while both PTYs stayed `40 120`. After the TUI client was killed the pane kept `44 114`.
- **PTY columns are not in the API.** `pane get` / `api snapshot` expose layout rects and `scroll.viewport_rows`, not PTY columns. A pane's layout rect equalled its PTY size when it was unsplit or a TUI client was attached, and differed after a headless split.
- **Resizing for real needs control.** Attaching a controller with `--cols 100 --rows 30` resized the PTY at once (`stty size`: `30 100`); `{"type":"terminal.resize","cols":90,"rows":25}` made it `25 90` and the controller's next frame was `full: true`, `seq 4`, 90×25. After `terminal.release` the PTY stayed `25 90`; after `kill -9` of the controller it stayed at the controller's last size (`20 70`). Not tested: whether it reverts when a TUI client is attached. Per source, layout resizes are suppressed while a controller owns the terminal (`direct_attach_resize_locks`) and the lock is dropped when the owner disconnects; the suppression itself was not observed, because a headless layout does not resize PTYs anyway.

**Consequence for the spec.** For observe-only panes, "re-rendered when the size changes" can only mean restarting the stream when Herdr's pane geometry changes, with the viewport matching Herdr's grid; warpr scales or scrolls that grid in its own surface. Reflowing text to warpr's size requires taking control (side effects on every other client), which belongs to the control slice.

### 2. Control: protocol, ownership, takeover

- **Stdin framing.** Newline-delimited JSON, one command per line; blank lines are skipped. Commands: `terminal.input` with `text` (UTF-8, verbatim) or `bytes` (base64), not both; `terminal.resize` `{cols,rows[,cell_width_px,cell_height_px]}` (zero rejected); `terminal.scroll` `{direction:"up"|"down",lines[,source:"wheel"|"page_key",column,row,modifiers]}`; `terminal.mouse` `{action:"down"|"up"|"drag"|"move"[,button,modifiers],column,row}` (zero-based cells); `terminal.release`. A malformed line prints `herdr: terminal session control input ignored: <reason>` on stderr and the stream continues. Stdin EOF is a detach, which is why `/dev/null` stdin produced `terminal.closed` / `detached` immediately; a held-open pipe keeps control.
- **Stdout.** The same `terminal.frame` and `terminal.closed` records as observe; the first frame is `full: true` at the controller's `--cols`/`--rows`. Targets accepted by observe and control: pane id (`w1:p1`), terminal id (`term_…`), agent name (checked with a pane registered via `pane report-agent` and `agent rename`).
- **Input is raw.** `terminal.input` bytes reach the PTY unchanged: `text: "echo typed-text"` appeared at the prompt without executing until a `"\r"` followed; `\x1b[A` arrived as `ESC [ A`. Neither `terminal.input` nor `pane send-text` added bracketed-paste markers with `?2004h` set. Frames do not carry application modes (see 3), so warpr cannot learn cursor-key or paste modes from the stream. `herdr pane send-keys up left` is mode-aware (`ESC [ A ESC [ D` normally, `ESC O A ESC O D` after `?1h`), so named keys SHOULD go through `pane send-keys` and text through `terminal.input`.
- **Mouse and scroll.** `terminal.mouse` is encoded for the application's mouse mode (with `?1000h` only: left down/up `ESC [ M SP $ #` / `ESC [ M # $ #` for column 3, row 2) and dropped when no mouse mode is set (a raw-mode probe received nothing). `terminal.scroll up 20` scrolled the shared viewport: a separate observer saw `242…281` instead of `262…300` and `pane get` reported `offset_from_bottom: 20`, so scrolling is visible to every client.
- **One owner per terminal.** `terminal session control`, `terminal attach` and `agent attach` share one owner slot. A second controller without `--takeover` received `terminal.closed` with reason `terminal attach failed: terminal term_… already has an attached client; retry with --takeover` and no frames; the first kept streaming. `herdr terminal attach` (run in a PTY) was refused the same way, printing `herdr: server shut down: …` and exiting 1. With `--takeover` (control, `terminal attach` and `agent attach` each tried) the previous owner received `terminal.closed` with reason `terminal attach taken over`; the new owner got a `full: true` frame at its own size.
- **Lock-out.** There is no hard lock: a refused client can always retry with `--takeover`. Ownership is not queryable (`pane get` has no field for it); attempting without `--takeover` is the safe probe, since the refused client is closed and the owner keeps streaming (per source the refusal returns before any resize). Observers are never refused: an observer at 120×40 stayed connected through the refusal and the takeover. Input through the socket API (`pane send-text`, `send-keys`, `run`) is not blocked by an owner and was typed into the pane while a controller held it. A Herdr TUI client typing during ownership was not tested.
- **Termination.** Every end of an `observe` or `control` stream that was seen exits 0 with a `terminal.closed` record, refusals included; per source only a failed connection or handshake exits 1, with a stderr message and no record. warpr MUST read `reason` (strings seen: `detached`, `terminal attach taken over`, `terminal attach failed: … already has an attached client; retry with --takeover`, `terminal session observe failed: terminal target <t> not found`, `terminal term_… exited` (shell `exit`; the pane is removed), `terminal attach ended: terminal … not found` (pane closed), `server is shutting down`). The reasons are prose, not codes.
- **`terminal attach` / `agent attach`.** Both need a real TTY (exercised through a PTY), render the pane into the caller's terminal, detach with `ctrl+b q`, and resize the PTY to that TTY's size (attach at 80×24 gave `24 80`). With no agent in the pane `agent attach` fails with `agent_not_found`. They add nothing over `control` for a GUI client.

**Consequence for the spec.** Take control runs `control` with a held-open stdin pipe and no `--takeover`, passes `--cols`/`--rows` equal to the pane's current size to avoid reflowing it for others, and shows the refusal reason when another owner exists. `--takeover` is only ever passed after an explicit user confirmation. Loss of control is signalled by `terminal.closed` with reason `terminal attach taken over`.

### 3. Rendering fidelity

- **Frame format.** Every frame is wrapped in `ESC[?2026h … ESC[?2026l` (synchronized output) and hides and restores the cursor (`?25`); text is painted with explicit `ESC[row;colH` positions, SGR, `OSC 8` hyperlink resets and `ESC[N q` for cursor shape. A full frame begins with `ESC[2J ESC[1;1H` and repaints every cell: feeding it into a grid pre-filled with other text left no residue, so frames can be fed straight to the VT without a reset. Incremental frames are diffs against the previous frame sent to that observer.
- **Wide, CJK and emoji.** `printf '漢字かな한글|X\n😀👍🏽🇯🇵|Y\ne\xcc\x81a|Z\nｗｉｄｅ|W\n'` came through with every wide glyph at its own `ESC[row;colH` (`漢` col 1, `字` col 3, `か` col 5 …, the `|` that follows at col 13), and the decoded grid matched `pane read` for CJK, Hangul and full-width text. Grapheme clusters (`👍🏽`, `🇯🇵`, `e` + U+0301) are emitted as one unit at their cell, so the cluster is intact in the bytes. `pyte` splits modifiers, flags and ZWJ sequences, so whether Warp's VT keeps them together is not verified here (no build was run).
- **Alt-screen applications.** `printf '\033[?1049h…'` replaced the observer's grid with the alternate screen and `\033[?1049l` brought the main screen back (`MAIN-MARKER` gone, then back). `less` and `vim -u NONE -N` rendered correctly; the observer grid equalled `pane read --source visible` in all 5 comparisons (idle, `less`, after `q`, `vim`, after `:q!`). The transitions are ordinary `full: false` frames: the stream contains no `?1049`, `?1000`, `?1006`, `?2004` or `?1h`, only `?2026`, `?25` and DECSCUSR. Observers see the current screen only, never scrollback; scrollback is available via `pane read --source recent` or `terminal.scroll`.
- **Heavy output.** `herdr pane run w1:p1 'clear; seq 1 200000; echo DONE-SEQ'` with an observer at 120×40: 61 frames, 31 897 bytes in all (largest 753 bytes) over about 1.3 s, median inter-frame gap 18 ms, no `full` frame, no disconnect, final grid identical to `pane read`. Herdr coalesces to about 60 frames/s. `seq` counted sent frames contiguously, so it cannot reveal dropped PTY updates. An observer stopped with `SIGSTOP` for 6 s during `seq 1 50000` stayed connected and, resumed, delivered 10 frames and the correct final grid. The docs say a socket write without progress for 30 s disconnects an observer; that was not tested.
- **Kitty graphics do not pass through observe.** A `a=T,f=24` Kitty image sent from the pane left no `ESC _` in any frame (the cells it reserved are blank). The observe CLI neither requests graphics in its handshake nor forwards them: `ServerMessage::Graphics { .. } => {}` (`terminal_sessions.rs`). `terminal attach` in a PTY also emitted none, but that PTY was not graphics-capable, so attach is inconclusive. Kitty images remain out of scope for observe.
- **Background panes.** A pane in a Herdr tab that is not focused streamed normally.

### 4. Why one run showed a single `full: true` frame

Most likely cause (reproduced): **the pane changed before the observer's first frame was produced.** After spawn the observer needs roughly 40–280 ms before frame 1; a change that lands earlier is already in that full frame and nothing follows. In 24 runs, with `herdr pane run w1:p1 'echo MK<i>'` issued at a random 17–440 ms after spawn, the 8 runs where it landed before frame 1 each produced exactly one frame that already contained `MK<i>`, and the other 16 produced 2–3 frames with the marker absent from frame 1 (24 of 24 agree).

Second cause (reproduced): **the change was outside the observer's viewport.** Frames are diffs of the viewport only; at `--cols 10 --rows 3` a pane change below row 3 produced only the first frame.

Ruled out, each of these still gave 1 full plus 1–2 incremental frames when the pane changed at 1.0 s: stdin `/dev/null`, held-open pipe or inherited; stdout a file or `| cat`; a `timeout 5` wrapper; the pane run issued from a backgrounded subshell; no `--cols`/`--rows`. Source agrees: the CLI flushes after every frame (`terminal_sessions.rs`). The original run cannot be reconstructed, so the race is the probable cause, not a proven one. warpr's pane stream must treat the first frame as a full snapshot of whenever it was taken, and must not infer liveness from a second frame.
