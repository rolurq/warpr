# warpr raises its own OS notifications and never suppresses on Herdr's account

Agents that become blocked or finish unseen work produce an in-app notification (toast and mailbox) and, while warpr is not the focused application, one operating-system notification naming the agent and its location. warpr decides this itself from the agent states it already follows. It does not read Herdr's notification settings, does not call Herdr's `notification.show`, and suppresses nothing because Herdr might deliver the same event.

## Why warpr cannot defer to Herdr's delivery

Findings from Herdr 0.9.4 (protocol 22), on macOS arm64, in the isolated session `warpr-test-31` with a throwaway config selected through `HERDR_CONFIG_PATH`; source references are to the `v0.9.4` tag of `herdrdev/herdr`. The user's own session and `config.toml` were never written.

- **Delivery needs an attached Herdr interface in every mode.** The server hands toasts and sounds to the foreground client shell, the private-protocol client that Herdr's own terminal UI is, and to nothing else (`send_notify_to_foreground_client`, `send_to_client_shells` in `src/server/headless/notifications.rs`). The OS notification (`osascript` / `terminal-notifier`) and the outer-terminal escape are produced by that client process (`src/client/notifications.rs`, `src/platform/macos.rs`), not by the server. `terminal session observe` and `control`, which are all warpr opens, are other connection modes and never count. With warpr as the only client Herdr therefore delivers nothing, whatever the mode. Observed: with `ui.toast.delivery` set to each of `off`, `herdr`, `terminal` and `system` in turn, `herdr notification show` answered `reason: disabled` for `off` and `reason: no_foreground_client` for the other three, and agent-state changes have no one to be forwarded to.
- **The mode can only be read from the config file.** The socket API has no call that returns configuration (`herdr api schema --json` has `server.reload_config` but nothing that reads settings back), and `herdr config` only has `check` and `reset-keys`. The file is `config.toml` in Herdr's config directory or wherever `HERDR_CONFIG_PATH` points for the server process, which a client cannot see.
- **Whether an interface is attached cannot be learned.** Nothing in the API, `herdr status` or the snapshot lists clients. The only probe is `notification.show`, which would show a notification on the attached interface if there is one; warpr must not use it.
- **Herdr's own notifications cannot reach warpr.** The only way to receive a toast, a sound or a `notification.show` request is to be a client shell. The event stream (`events.subscribe`, `pane.agent_status_changed`, `pane.output_matched`, `pane.scroll_changed` and the broader `EventKind` list) has no notification event, and plugin event hooks (`[[events]]` in a plugin manifest) fire for the same `EventKind` list. Speaking the client-shell protocol is the undocumented binary protocol ADR-0002 declined.
- **Notification escape sequences do not survive.** A program in a pane wrote `ESC ] 9 ; text BEL`, `ESC ] 777 ; notify ; title ; body BEL` and an OSC 0 title; neither `terminal session observe` nor `control` carried any of them (the frames held only the visible cells `ABCD`, cursor positioning and `OSC 8` resets, and no BEL). Nothing is delivered that way and nothing is suppressed on its account.

## Consequences

- Suppression would be wrong in the only situation warpr can see: no Herdr interface known to be attached means Herdr delivers nothing, and an attached one cannot be detected. So warpr always raises its in-app notification and, when unfocused, its OS notification. A user who also runs a Herdr interface with system delivery may get both; warpr cannot tell.
- warpr's OS notifications play no sound of their own, leaving sounds to Herdr's own, and record no telemetry.
- Herdr's own notifications (`notification.show` from agents or other clients) cannot appear in warpr's in-app surface until Herdr offers a way for a non-shell client to receive them. What warpr would need from Herdr: an event or subscription that carries each notification Herdr would show (title, body, sound kind, the pane and agent it concerns when it has one), delivered to API clients regardless of delivery mode; and a way to learn the effective delivery mode and whether an interface is attached and able to deliver, so that suppression could be exact.
- Seen state is held per window and the focused window decides, so it never depends on which window reported last. Only the focused window's selected workspace and the panes its selected Herdr tab shows count as seen; the agent panel covering the tabs counts as not seen.
